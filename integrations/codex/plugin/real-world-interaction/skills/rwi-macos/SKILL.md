# Real World Interaction — macOS

Read the sibling real-world-interaction skill first and retain its selected device identity. Require `platform=macos`; never select a Windows target to work around a Mac failure.

- Read live capability and permission facts. Global tool discovery does not prove that lifecycle, visual capture or any other action exists on this Mac agent.
- A discovery page is a native window inventory, not a main-window selector. Never use `windows[0]` merely because its PID matches: Colors, Fonts and other panels may precede the document. Match the exact known native window ID, or compare the freshly observed title, bounds and intended surface before attaching; titles do not prove ownership.
- Select a fresh PID/window/native epoch. When `computer.attach_window` is implemented, attach through the original desktop target and use the newly returned target for each window/panel; its binding is fixed and does not replace another window or Live source. Release its lease before `computer.detach_window`; detachment does not close the app. Older agents require explicit `bind_window` and fresh observation when switching back. Selection is not proof of focus or movement.
- `discover` reports current active displays and each window's containing display. Prefer the current ColorSync `uuid` for an allocated BetterDisplay virtual screen; numeric `id` and coordinates are transient. Re-discover after reconnect/layout changes. A UUID identifies a display, not an independent session or input lease.
- `capture_visual` is a response-only exact-window screenshot without an AX walk or input frame. It excludes separate system panels; discover and explicitly bind a panel after verifying its native identity. Do not turn a visual pixel into an input coordinate/reference. It is not the Codex session Live overlay.
- When `capture_visual.containing_display_required=false` is advertised, an exact on-screen window can be captured even if its full bounds do not fit one display. `capture.details.display:null` remains unassigned, not permission to substitute a monitor or send input. Normal snapshots may also show that window with `mutation_ready=false` and no desktop pixel mapping. Keep these read-only results separate from input/focus/placement readiness; never replay a refused action or borrow the response-only visual transform as an input reference. Hidden/minimized discovery remains unsupported unless independently advertised.
- A newer native `mapping` descriptor may advertise exact on-screen window SCK/AX point bounds instead of full single-monitor containment. Only a fresh normal snapshot with `mutation_ready=true`, an actual desktop mapping and valid frame/view can provide input references; `display:null` remains descriptive. Each native operation still rechecks the pinned window/process/session, geometry, content, element/modal state and lease. Fully offscreen or affected rotated surfaces remain unavailable. Explicit `foreground_system` pointer movement additionally requires exactly one unrotated active display at the point; do not clamp an offscreen point or silently switch delivery after refusal.
- Some CrossOver/GameHub/Wine or other nonstandard windows may have a discoverable CGWindow and capturable pixels but no matching Accessibility window. Their titles can be absent or belong to a host process, so prefer fresh exact-PID discovery and verify the actual owner instead of a title match. On a version that reports `computer.snapshot.visual_only=true`, use the returned image or `computer.image` native tile only for observation. `binding`, controls, and a resolvable `view_id` are absent: do not click, drag, or infer coordinates from those pixels. An exact `AXWindows` read failure (-25204 after bounded settle, unsupported, or no value) may return a read-only picture while preserving its original `consistency.ax_error`; this does not prove AX absence, input compatibility, or complete capture. Identity ambiguity, permission denial, other AX failures and capture failures remain errors. Obtain a fresh positive input binding before any action.
- A Wine game may instead expose an exact AX window **with zero child controls**. In that case `visual_only=false` and a pixel view may be available, but this proves only window/pixel grounding, not semantic control support or that the game will accept a synthetic event. Do not treat the launcher PID as the rendered game's PID; use the independently discovered window owner. Keep any authorized interaction non-disruptive and verify its effect separately.
- For small text, request `computer.snapshot` with `max_edge: 2048`. An updated gateway uses this by default; a previously loaded task may still use the older 1024-pixel default. If the source is wider than 2048 pixels, use the returned `observation_ref` with `computer.result` at `/artifact_id`, then call `computer.image` with an original-pixel crop for a native-resolution tile. Do not claim unreadable source pixels can be restored by enlarging them.
- If the loaded catalog advertises computer.show_native_live, use that typed entry for an explicitly authorized **independent native overlay**, with options.display selected separately from the source. It does not need MCP Apps, a browser tab or Host presence, and changing chats does not hide it. Native source/context identity, permissions and bounded lifetime still apply; use computer.live for status/hide/resume/stop and independently verify real frames and native controls. Stop the existing preview before changing modes; do not fabricate visibility, borrow a denied Host observation route, or treat a start receipt as visible pixels. computer.show_live remains the separate conversation-component route.
- With a loaded schema that makes `computer.show_live.options.display` optional, omit `display` for read-only cached PNG inside the conversation with no native overlay. Specify an explicitly selected viewer display to also show the native panel. Ordinary `computer.live` start retains its explicit-display compatibility route. Older loaded schemas may still require display: never work around that by supplying private `host_image_only`, `host_view_id` or `view` fields. Stop the existing preview before changing presentation; use `computer.live` separately for status/hide/resume/stop rather than replaying start.
- If `viewer.resource_uri` is returned, the Host negotiated MCP Apps and may render the conversation image and controls without a separate browser tab. Its app-only presence/image bridge cannot select another target or send input; do not call it from the model or fabricate visibility. If `viewer.url` is returned, the browser compatibility route was selected; open that exact URL with `open_in_codex` in the current task. Neither route attests an active Host task ID. Public navigation success alone is not proof of automatic hiding: independently check the actual component and native status, and retain contrary or missing evidence.
- **Where the user sees Live:** newer conversation components render cached pixels; an additional native floating panel exists only on the explicit-display route. Keep source selection independent of viewer placement. A virtual-screen source does not authorize choosing a physical viewer display. Confirm actual image decoding/visible bounds rather than inferring user-visible pixels from counters or a resource URI. Hide can be restored within the same live session; Close/stop is terminal and reopening requires a new observation. Check actual cleared/stopped state; this does not prevent screenshots by other software. Task switching has not been generally attested, so do not promise strict per-task privacy.
- With a compact-presenter Agent, Live image detail (`max_edge`) is independent of the small aspect-fit panel bounds. Read the actual presenter bounds/display; a 2048-pixel capture does not request a 2048-point panel. Inspect fine text with an exact-window snapshot or native-resolution tile instead of enlarging the floating preview.
- On the explicit native-panel route, require `presenter_readback.on_requested_display=true` and bounds inside the requested viewer display before claiming placement. Hide/stop a misplaced panel; a returned start alone is not placement proof. Conversation-only status instead reports no requested viewer display and no native presenter window; do not reinterpret those nulls as a missing-window failure or an implicit display choice.
- For explicitly requested foreground activation, prefer the loaded `computer.bring_to_front` with the selected `target` and stable `request_id`. It handles fresh observation, the full current foreground identity, window reference, short lease and release internally through the existing native `focus_window` guards. Verify a fresh foreground readback; a receipt is not goal proof. Unknown/unsupported states refuse, without keys, mouse, unhide/restore or retry. Never use activation as a silent fallback for background input.
- Prefer `computer.place_window` for moving the already selected window to a display UUID: it handles fresh observation, reference and lease in one bounded call. `placement_confirmed` requires the requested origin, not merely presence on the display; re-discover independently. A returned AXPosition call can be ignored by an app (observed with a Paint S Save Sheet), so do not replay or claim visual movement from its receipt.
- Use observed AX roles, enabled state, advertised actions and current selected/value fields where present. Missing attributes are unknown, not false. An incomplete AX tree does not prove the control is absent.
- **Background Unicode readback:** `type_text` returning `dispatch:"returned"` is not a text-effect acknowledgement. Independently snapshot the same authorized plain field and compare the full intended result, including non-BMP characters, combining marks and joiners. Local field focus does not prove page/widget or OS foreground focus; an inactive Chrome 155 case accepted key events but omitted non-BMP text even after advertised AXPress. Preserve the original request when the result differs; do not repair it by replay, silent activation or an unrequested AXValue/clipboard/browser-content substitution. Never split UTF-16 surrogate pairs. An AX attribute reported settable is not proof its provider performs insertion.
- When returned, `text_effect.state` distinguishes `value_matches_expected`, `value_differs_observed` and `unknown` using a bounded plain-field value/UTF16-selection sample. It is not event causality or goal verification. Missing evidence remains unknown, including older gateways that omit this extension; a mismatch never authorizes replay or a different input route. Readback failure does not itself mean input was rejected.
- For value readback, inspect the exact snapshot element ID's inline `value` first: `value:""` is known empty; missing/null is unknown. Check both `value_truncated` and `display_truncated`. For a small retained detail, use that same snapshot's `details_ref` with `computer.result` at `/elements/<index>` or its `/value` child; derive the index from this response, not another frame or the raw scene array. Retained reads send no Native RPC/input and do not refresh the frame. Full-root byte export is optional audit, not required for a short value; it cannot recover Native-truncated text or turn a receipt into a DOM goal.
- `window_missing` means the exact target was absent from the on-screen lookup, not necessarily destroyed. When `diagnostic.native_record_present=true` and `owner_matches=true`, an independent exact-ID native description still exists; `native_onscreen:null`, `hidden:null` and `destroyed:null` remain unknown. This diagnostic supplies no image, frame or input authority. Independently refresh discovery; any supported focus/placement is a separate explicit action, never an automatic retry, unhide or replay of the failed input.
- For an exact observed control advertising `AXPress`, request that native action explicitly with `computer.click at.action="AXPress"`; it is semantic execution, not a pointer click. Native window/object/provider/ancestry/modal/enabled/action/state checks still apply. A covered sibling window's button can accept this action without pointer hit visibility; ordinary point/mouse clicks retain positive visibility checks. Never automatically downgrade a refused path to another one.
- New snapshots expose `consistency` and `coverage`: pixels precede post-capture controls and are not atomic. Unrelated dynamic text may change during a valid read-only snapshot; every action still revalidates its target. A single post-capture control walk follows a lightweight pre-capture window/modal/context guard. `semantic_content_changed:null` means no before-tree comparison was collected, not semantic equality. Coverage reasons (depth/node/queue/time budgets or unavailable reads) explain omissions, not absence. Old loaded gateways may require `computer.result observation_ref` at `/adapter_status/observation_consistency`; missing coverage is unknown.
- Cooperative activity detection uses a combined-session timer, not proof of a physical human. For explicit native semantic actions with known foreground/focused-window identity, another exact same-app window does not inherit this target's gate. Synthetic delivery may prepare a shared application receiver, so its same-app gate remains conservative; unknown same-app window identity also yields. Refusal diagnostics distinguish combined-session and HID-table ages but do not attest an event's source. Do not disable genuine user yield or replay to overcome it.
- Use the capture's current pixel-to-desktop transform. macOS points, Retina image pixels and canvas coordinates differ; never apply a Windows pixel offset or assume scale=2. Re-observe after display changes, scrolling, window geometry changes or panel opening.
- Discover all current windows after opening a panel. On the current macOS backend, `owned_popup` / `return_to_owner` transitions are not implemented; use a fresh explicit `initial` selection of the actual authorized window instead. This does not assert ownership, activate it or move it. An ordinary sibling window is not necessarily an owned popup; same PID does not identify the input receiver. See [multi-window recovery](references/multi-window-recovery.md).
- Some macOS dialogs expose a logical AX window distinct from their rendered CG window. A discovered `semantic_only` window has grounded AX controls but no bitmap or pixel mapping (`visual_available=false`). Use only explicitly advertised AX actions for input; a window-level `computer.place_window` may be attempted, but it confers no pixel input authority and its logical readback does not prove that a separate rendered surface followed. Never borrow pixels from another window. Binding it preserves the last explicit Live visual source and does not assert that the two window IDs are aliases.
- An AXModal popup can be actionable even if Paint S leaves `AXFocusedWindow` on its document. Bind the exact discovered popup; the native agent requires the popup's own hit-tested AXWindow/PID/CG ID before enabling its controls. Do not infer this from title or same PID.
- Respect current foreground and keyboard-element prerequisites, cooperative human yield and durable input fences. Do not downgrade a refused action to another input path.
- Window-addressed pointer grounding may independently resolve a real descendant of the exact selected AX window when the application hit names a sibling panel or misses the actual point. It does not borrow that panel’s identity or authorize another receiver. `foreground_system` still requires a positive physical hit in the exact selected foreground window; it cannot inherit this background proof. A rejected route never automatically changes delivery or replays input.
- Background `CGEventPostToPid` is an addressed attempt, not an app-effect acknowledgement: an unfocused application may ignore a drag even when the receipt says `returned`. For application drawing, compare native pixels and the editable layer state after each distinct stroke; a selection overlay is not artwork. Confirm the active tool after focus changes, and do not replay an uncertain input merely because its receipt returned.

Use only the current tool schemas. Historical macOS observations are documented in the shared [workflow reference](../real-world-interaction/references/native-workflow.md); they are not guarantees for every application/version. For Paint S acceptance, preserve non-reproducible source imagery as independent image layers and verify placement in the actual application.
