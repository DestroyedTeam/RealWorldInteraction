# 多端通用 RCU：架构纠偏与评审输入

状态：**用户需求已明确；CONTROL CENTER 设计评审中，尚非已批准架构。**

## 用户确认的产品方向

- 无自有产品 UI，以 MCP 工具、Plugin、Skills 对接 AI Agent。
- 面向多端，而非固定 Mac 与 Windows 的双端应用。当前优先完成 Mac/Codex 接入及 Windows 实机验证；设计需考虑本机、远程主机、虚拟机及 Windows、Linux、macOS、Android、iOS。
- 受控端安装独立、无界面的原生 agent，提供该平台实际具备的观察、截图、输入和结果能力。未实现或受平台限制的能力必须明确报告。
- 后续可扩展至其他物理设备。现在建立清晰的能力/适配边界，不宣称已支持家电，不为远期愿景提前堆积框架。
- 业务任务由 AI 或调用方组织；“修改记事本”“清理 CrossMacro”不得成为服务建链、启动和通用工具可用性的前置条件。

## 术语待架构文档明确

AI Host 是 MCP client；向 AI 暴露工具的是 MCP server/adapter。受控 agent 与该 adapter 的网络连接角色、主动/反向连接方式，不应混淆为 MCP 的 client/server 角色。MCP adapter 的部署位置及其与受控端之间是否使用独立协议，由评审说明取舍。

## 当前被否定的耦合

`Approval` 文件/文本目标和固定八阶段验证流程被放进了 native-link 生产连接路径。窗口或业务步骤失败引发的 HOLD 因而阻断新 MCP 会话。预准入诊断模式仅改善可见性，新增 `ProcessCleanupSeed`、`ProcessAbsenceGoal` 仍未解决这一根本问题。

停止继续扩展上述业务专用路径。现有改动与现场失败证据先保留，待评审逐项决定保留、迁往测试、替换或移除；不执行整体 Git 回滚，不清除历史操作记录，不把未完成代码作为已验收架构发布。

## 评审要求

1. 明确 deployment、service、transport、client session、target capability、operation authorization、action reservation、evidence 和 business orchestration 的边界及独立生命周期。
2. 保留认证、目标身份绑定、输入互斥、操作授权和防重复执行；将失败和不确定性限制在恰当范围，不能把具体业务失败变成整个服务的永久失效。
3. 依据参考源码及官方协议建立可追溯对照，不以“Rust 重写”替代兼容性证据。
4. 给出 Rust workspace 依赖方向、现有代码处置清单、可评审的小步迁移顺序及实机验收矩阵。

## 最低验收边界

- 不打开任何指定应用，MCP 服务仍可初始化并列出工具及明确的目标状态。
- 关闭目标窗口，仅相关窗口操作失效；服务和其他目标仍可用。
- 设备离线、权限不足、一次操作失败，不应使无关客户端的只读操作失效。
- 更换业务任务或建立新会话，不必重新编写或部署任务专用后端。
- 多目标路由、身份和权限不混淆；重连绝不自动重放输入。
- 分别报告服务可用、设备连接、原生操作和业务结果，不相互冒充。
