用户指定的是 **清理 Windows 虚拟机进程**：
`01a09395-5b92-7812-ba25-878aceb09466`，回合
`01a09396-3d3a-7b83-b373-0a72279189a0`。

**557.308 秒，即 9 分 17 秒**。用户所说的九分钟是正确的。

本轮只读该任务的完整日志与项目源码，没有重新结束进程、重放输入或复测 GUI。
任务最终报告筛选结果为空、等 10 秒复查仍为空；这里审计其执行记录，不把

## 2. 完整时间账，而不只统计 MCP

| 项目 | 实际记录 |
| --- | ---: |
| Host 整轮 | 557.308 s |
| 126 次 MCP 调用时长合计（原始高精度 duration） | 108.146 s |
| Host 工具执行区间并集，含 MCP、显式等待和包装代码 | 119.901 s |
| 每批工具输出完成 → 下一工具提交/最终回复，累计 | **426.820 s** |
| 首次工具提交前 | 10.392 s |
| 最终消息后到回合结束 | 0.103 s |

日志起止及上述不重叠区间相加为 557.216 s；与 Host 单调计时的差为
92 ms，保留两种来源，不人为抹平。MCP 的区间并集是 108.186 s；它与
108.146 s 高精度调用 duration 之和的微小差异来自事件端点精度。

工具执行区间包含一次约 10 秒的明确 `clock.sleep`，不能把它算成模型思考。
每批返回后的间隔 p50 **10.926 s**，nearest-rank p95 **42.136 s**，样本 30。

“理解/思考耗时”的可观察口径为 **结果交回 Host → 下一调用已生成/提交**，
包括模型读取、规划、旁白、调用代码生成及 Host/推理服务调度；不能声称已
单独分离纯推理计算。它是主要体验指标，绝不能从总效率中剔除。

### 全部记录，不挑短样本

- `2026-09-12-crossmacro-mcp-timeline.csv`：**126 行**，每次 MCP 的时间、
  状态、输出量、到下一 MCP 的间隔，以及是否属于同一代码批次。
- `2026-09-12-crossmacro-model-handoffs.csv`：**30 行**，每批工具返回到下
  一步的间隔、旁白量、下一个模型响应的输入/输出/reasoning token 计数。
- `2026-09-12-crossmacro-flow-summary.json`：可机器读取的汇总。

实际是 **29 次 `functions.exec` + 1 次 sleep，31 次模型响应**。
126 次 MCP 之间，有 **99 次相邻转换在同一个 exec 内**，只有 **26 次跨
exec**。不能给每个内部 `await` 都贴上“模型又思考了一次”的标签。
原生调用表的跨批次间隔还可能包含 sleep/其他工具；准确的模型交接成本看
批次表，二者不重复相加。

## 3. 哪些实际问题放大了耗时

### 3.1 输出与上下文

本任务工具可见文本累计 **219,890 UTF-8 字节**，另有 4 张图片，未把图片
当文本字节。首次元数据/Skill 加载批次约 40.2 KB，首个 observe 的可见输出
也约 40.2 KB；**这两份都已有明确的 Host 截断提示**。首个 observe 的单份
原始 structured payload 实际为 **82,003 字节**，回显提示原始约 20,407
tokens，而模型没有获得完整文本。原始 MCP 同时带 text/structured，但该
observe 回显选择的是单份结构化数据，仍然过大，不能只归咎于 wrapper 重复。
需要缩减默认诊断/树结构并提供完整证据按需读取，不能只提高输出上限。

记录的模型是 `gpt-6-astra`、`max`；31 次响应的输入上下文从 **29,821**
增长到 **124,076 tokens**。累计 reported output tokens 为 11,684，其中
reported reasoning tokens 3,202；后者不是额外加到 output 上的数量。
这不是某个工具独占 token 数，也不能由它推算纯推理秒数。
本轮没有改模型/effort，也不通过降模型设置回避接口设计问题。

### 3.2 持有租约期间回到模型，产生真实失败

- 11:11:09 的批次申请 **15 秒**租约，执行 `Ctrl+A` 和观察。
- 返回后到下一批次提交间隔 **10.926 秒**。
- 再次 Text 调用提交时，距 Host 收到租约已 **14.416 秒**，最多只剩约
  584 ms；它又经过约 **1.669 秒**原生前置检查。
- 返回 `lease_required`，并明确 `native_dispatch_entered=false`；随后
  release 返回 `unknown_lease`。后续增加 durable request 查询、值验证、
  新租约和新的受控动作。

这不是把某个失败当作“网络慢”：**模型交接间隔直接消耗了资源租约**。
正确改善是先决定动作，再在同一个有界执行单元中申请/执行/释放，而不是
把一段 15 秒租约跨模型回合传递，也不是无限延长租约或自动重放输入。

### 3.3 原生路径也确实有成本

| 工具 | 次数 | 合计 | 单次 p50 / p95 |
| --- | ---: | ---: | ---: |
| `act_checked` | 29 | 61.745 s | 2.518 / 2.804 s |
| `observe` | 46 | 35.783 s | 0.864 / 1.107 s |
| `verify` | 11 | 10.000 s | 0.933 / 1.801 s |

这些是完整 MCP 调用时长，不是纯网络或纯 FFI 分段。
源码另外确认：`checked_action.rs` 调一次 backend `revalidate`，进入
`Engine::act_inner` 后再调一次，Windows backend 的 `act` 又调一次；
某些 agent-input proof 分支还会增加校验。Windows `revalidate` 会走
`scene` 内的 UIA walk。语义元素路径不必抓 PNG，但仍可能重复完整 UIA 遍历。

因此应分析如何复用有界校验结果、保留临门的身份/焦点/元素/租约检查，
而不是为了快删掉保护。这个源码结构是确认的；各段的精确占比仍需 native
span，不能凭 2.5 秒整包时间分摊。独立的目标结果验证也不能合并成输入回执。

### 3.4 优先级调整

1. 减少全树/诊断重复输出，建立可直接选择下一步的紧凑状态。
2. 提供持久通用资源对象与助手，避免每批重复生成数千字符的控制代码。
3. 将必要动作/新状态组成有界批次，租约不跨模型等待，失败立即停止后续动作。
4. 为重复 UIA 校验与图像编码增加分段测量，再优化原生实现。
5. 最后结合真实 RTT 样本优化连接复用；不能只盯两个 status RPC 或握手速度。

## 4. 双通道：采纳职责分离，不把两套权限混成一套

用户补充的方向可纳入 ADR 0002：同一个设备注册表下提供两个**逻辑通道**。
具体 SSH provider/终端 API 仍是待实现设计，不宣称已有 RCU SSH 工具。

```text
AI Host / 通用 SDK
  ├─ GUI 通道：Rust MCP → authenticated device RPC → Rust native agent
  │             截图、AX、鼠标键盘、窗口状态、执行查询/取消
  └─ Terminal 通道：明确选定的本机执行器或 SSH client → 目标 terminal service
                exec、交互 PTY、stdout/stderr、退出状态；按需文件传输
```

- GUI 通道负责真实界面，不仅是视频流；输入/取消控制不能被大图片阻塞。
- SSH 通道用于精确进程/文件/日志/构建等适合终端的工作。SSH 能完成用户
  目标时，不必人为绕到任务管理器点十几遍；反过来，GUI-only 验收不能拿
  SSH 结果冒充原生鼠标键盘验收。
- 本机不必绕 SSH：Skill 可以在已授权的本地终端与 RCU 之间选择高效手段。
  这不会把 Rust GUI 后端变成 Python/PowerShell 隐藏桥；终端是明确可见的
  独立用户能力，不是伪装成 `computer.act` 的实现。
- 两通道共享设备登记和关联审计标识，但分别认证/授权。GUI mTLS pin 与
  SSH host key 必须在配对时明确关联，不能仅凭同一 IP 就认定是同一设备。
  SSH 用户/权限不一定等于 GUI 桌面 session，特别是 Windows。
- 两通道可以连接并存，但对同一进程/文件/应用资源的写操作需协调；终端
  重启/结束进程后，GUI 旧 HWND/PID/frame 不再可信，要重新发现/绑定。
- 一条通道离线不能锁住另一条。终端大 stdout 也不能阻塞 GUI 的取消。
  “两条逻辑通道”不强制等于永久开放两个 TCP 端口；端点与连接复用属于部署选择。
- 普通 SSH 不自动提供 exactly-once/durable receipt。SSH 断开或本地 ssh
  退出不等于远端命令没执行；有副作用的命令禁止盲目重发，必须查询可用的
  执行状态/目标结果，无法确认时保留 uncertain。
- Android/iOS/其他设备不应因为没有 SSH 就被整体禁用；终端能力按平台
  如实报告，不做假通用支持。

### Windows SSH

Windows 11 可以使用 OpenSSH Server；Microsoft 的内置可选功能是支持的
接入途径。但 Server 是否安装/启用、账户和终端环境是否适用，需要在该 VM
上单独检查，不能仅凭 OS 名字说已可用。
[Microsoft OpenSSH 文档](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_install_firstuse)

本轮未安装/启动 sshd、添加用户密钥或开放 22 端口。此前防火墙授权只有
Mac→Windows 的 TCP 45128；讨论 SSH 架构不自动扩大这条已批准规则。

## 5. Proxyman 与后续实际对标的使用边界

用户允许必要时用 Proxyman 并操作其他应用；本轮尚未进行实际抓包或 CUA
对标操作，也未把“不能控制 VM”的用户反馈记为已独立复现的结论。

已读取的 Codex JS 路径是：REPL → trusted RPC → 本机 native pipe → native
service。Mac 的该管道是 Unix domain socket，不是 HTTP；Proxyman 的
HTTP/HTTPS 代理不能直接解释它每次 AX/点击的内部耗时。
Proxyman 可分析确实经过它的 HTTP(S) 请求/响应与流式时间；部分终端运行库
并不遵从系统代理，需要显式配置。不能把“没抓到 HTTP”当作“没有 native 调用”。
[Proxyman 官方说明](https://docs.proxyman.com/automatic-setup/manual-setup)

若做后续对标：

1. 用独立的无敏感内容应用/窗口做小型确定性操作，不用 VM/RDP 鼠标问题
   当作这次基准；先固定目标、初始状态和相同的用户目标。
2. 同时记录 Host 批次边界、模型输出后续接间隔和 native IPC/应用状态。
   只看网络请求时间仍然漏掉用户关心的模型接续成本。
3. 存在实际 HTTP 链路时才启用限定目标的 Proxyman capture，不扩大为
   全机流量解密，不复制令牌/正文进 Git，不修改证书 pin 来强行抓包。
4. native 的 AX diff/稳定等待算法未有完整源码或有效 trace 时继续标记未知。
   比较本机 socket 与远端 TCP 必须分层，不直接得出工具总体快慢排名。
