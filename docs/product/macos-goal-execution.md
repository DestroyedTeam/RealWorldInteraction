# Goal｜RWI Mac 集成可交付版本收口

## 一、最终目标与责任

在「Real World Interaction：Mac端」会话中，完成一个功能边界明确、能够实际使用、具有完整验收证据、可回滚，并通过现有公开 PR 交付的 Mac 版本。

完成目标不等于写完文档、跑通单测、提交代码或推送 PR。只有下述必需功能、验收、回滚和交付条件全部满足，才能标记 Complete。

首选明确授权显示器上的非激活原生小浮层，独立于当前业务标签页。

通过条件：

- 宽度不超过 320 pt，高度不超过 360 pt，控件不被裁剪。
- 保留源图比例和清晰度。
- 在一次 5 秒手势中显示至少 3 个不同源帧。
- Hide、Resume、X 关闭分别验证。
- API stop 成功不能替代用户点击 X 的验证。
- 独立原生浮层不以切换聊天作为关闭条件，但仍受明确的目标、会话、授权、租约和停止生命周期约束。

### M15：会话内 Live 与 Host 生命周期

通过条件：

- 在真实 Host 中验证 PNG 解码、眼睛按钮、恢复、X 关闭和实际显示容器。
- 组件内容宽度不超过 320 CSS px。
- 不要求不可控制的 Host 外框与其他产品 UI 像素级一致。
- 真实可见性丢失后，按照下面的时间标准停采和清图。
- Host 不提供必需的身份、事件或观察通道时，准确记录外部依赖，不伪造事件、不反复新建聊天碰运气，也不换通道绕过明确的访问拒绝。

Live 的统一计时标准：

- 本次核对源码的 presence lease 为 1500 ms，采样间隔为 500 ms。
- 隐藏或会话内真实可见性丢失后，2 秒内清图并停止采集。
- 此后相隔 1 秒的两次状态中，capture 计数不得继续增长。
- Resume 后 2 秒内显示同源新帧。
- X/Stop 后 5 秒内观察到 `stopped`、`worker_done` 和清图。
- 以上是本次验收标准，不是已经取得的成绩。测试前冻结数值，不得根据结果事后修改阈值。

### M16：性能与输出

固定三个场景：

- snapshot；
- input receipt；
- Live read。

每个场景采集 5 个样本。

通过条件：

- 分别报告中位数、最大值、调用数和返回字节数。
- 工具墙钟时间、Native 执行时间和编排时间分开。
- 关键控件、错误信息和 PNG 不丢失。
- 没有公平基线时，不宣称速度或 CPU 使用优于 Computer Use。
- 不用 5 个样本作可靠 p95 性能承诺。

### M17：最终回归与回滚

在唯一根 workspace 执行：
```css
rtk cargo fmt --all -- --check
rtk cargo test --workspace --locked
rtk cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
```

缓存依赖足够时使用 `--offline`。

通过条件：

- 三项命令退出码均为 0。
- 相关 Live Node 测试和架构检查通过。
- 忽略测试逐项说明范围和原因。
- 独立副本回滚后 hash 与原件一致，并能够重新应用修改。
- 不回滚生产工作树。
- 不以历史回归或旧 HEAD 的 CI 替代最终候选验证。

### M18：公开 PR 交付

通过条件：

- 使用明确路径暂存。
- 按职责合理拆分 commit。
- 正常 push 到现有公开 PR。
- 远程 HEAD 与最终候选一致。
- 对应 HEAD 的 CI 成功。
- 返回仓库、PR、HEAD 和已知限制。
- 不自动 merge，不创建 tag，不发布 release。

## 五、证据、复验与重试规则

每个用例执行前记录：

- case_id；
- 前置身份和版本；
- 输入；
- 独立预期结果；
- 证据层；
- 超时；
- 清理方式。

执行后记录：

- 实际输出及退出码；
- PASS、FAIL、UNVERIFIED 或 BLOCKED；
- 绝对证据路径与 hash；
- 实际耗时；
- 缺口和下一动作。

离线测试、真实 MCP 进程、Host 实际加载工具、Native 效果、Host 像素和性能分别判定，不能互相替代。

只有相关输入或代码依赖变化，才使旧通过证据失效。新增门槛只复核受影响项目，不整表清零。

每个问题先最多进行两个不同、可证伪的假设实验。同一 BUILD 最多建立一个新的 Host 验收聊天，并发验收聊天最多一个，优先复用已有合格会话。

遇到外部依赖，先推进其他独立事项。当全部有意义路径都被同一外部条件阻塞，且连续三个目标轮次满足工具规则时，才将目标置为 blocked，并给出具体解锁条件。

如果只是需要更多工程时间，应说明具体下一假设和有界估时，不能伪造外部阻塞。保留失败记录，不重放 uncertain 输入，不自动切换输入路线掩盖失败。

## 六、必须交付的六类产物

### D1：源码与配置

交付最终源码、配置差异、构建身份及适用范围。

只修改 RWI 相关配置，保留配对、证书、权限和其他 Host 服务。不提交秘密、本机设置、二进制或原始截图。

### D2：当前验收表

交付一张覆盖现有 51 个子用例的验收表，至少包含：

- 输入；
- 预期；
- 实际；
- 状态；
- 证据层；
- 版本指纹；
- 耗时；
- 缺口。

新用户批准的用例可以在新版本中明确增减，但不能偷偷改变分母。

### D3：中文验收报告

简明中文说明，按真实时间排列步骤和原始截图链接。

每一步明确结果或问题，已验证与未验证分开，不能使用重绘或替代画面冒充原始验收截图。

### D4：运行与清理证据

交付配置、部署文件和实际加载身份的对照，以及清理、租约释放、禁止重放证据和已知限制。

### D5：可逆修改产物

沿用已有四角色：

- `MODIFIED_FILE`
- `DIFF_FILE`
- `VERIFICATION.txt`
- 可执行的 `ROLLBACK.sh`

在独立副本验证基线、修改、回滚、重应用及原 hash 恢复。

### D6：Git 与 CI 交付

交付现有公开仓库和 PR 地址、合理 commit 列表、远程最终 HEAD，以及该 HEAD 的 CI 结果。

## 七、完成判定与汇报格式

只有同时满足以下条件，才能标记 Complete：

1. 所有必需用例 PASS；不适用项目具有用户明确批准和理由。
2. 没有未解决的核心功能缺陷、安全缺陷或外部阻塞。
3. 最终相关回归、清理和回滚通过。
4. D1–D6 全部存在、可打开，内容与实际证据一致。
5. 最终源码、部署范围、远程 HEAD 和 CI 的对应关系清楚。

文档写完、用例分类完成、push 完成或时间耗尽，都不能代替上述条件。

每个阶段仅汇报：

- 当前阶段与已用时间；
- 新增 PASS、FAIL、UNVERIFIED、BLOCKED 数量；
- 实际变更和证据；
- 剩余必需项；
- 下一可执行动作或外部解锁条件。

首轮八小时报告额外给出交付判定和剩余工作的有界估时。不要高频复述没有变化的状态。

## 八、新增需求与目标演进

后续收到用户新要求，由原 Mac 执行会话将其整合为本 Goal 的新有限版本，同时更新验收标准、交付条件和受影响用例，不依赖其他审计会话持续维护。

保留未被明确替代的旧要求，消除重复和冲突。只有真正受影响的用例需要重新验证，其他有效证据继续沿用。

Goal 是目标和完成条件的权威。项目 JSON、Markdown 是执行记录、证据索引和镜像，不能反过来凭文件内容生成新的用户任务。

如果持久 Goal 编辑接口不可用，必须准确区分“新的执行指令已采用”和“App 内 Goal 原文已更新”，不能冒称更新成功，不能绕过安全拒绝、直接写数据库，或虚假完成旧 Goal 后另建一个重复目标。
