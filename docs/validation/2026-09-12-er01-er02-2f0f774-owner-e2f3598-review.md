## 3. panic 时 fence 必须先于 permit 释放

**候选定位：** `/Users/vincentadamnemessis/AI Projects/Real Computer Use/crates/rcu-agent/src/runtime/dispatch.rs:12–25,155–191`。

此前分开的 panic fence 和局部 permit 容易受析构顺序影响。现在 `WorkerOwnership` 的 Drop 先写入 fenced，之后才释放其持有的 context/input permit 字段；正常错误路径仍在释放前记录不确定性。worker 继续持有 Runtime/Context 的 Arc 和 Finish，不因 async 等待方消失就释放 native 执行所有权。

单测检查 panic 后 fence=true 且 permit 归还。这个单测的终态断言本身不能区分所有旧的中间竞态；“先 fence 后释放”的结论同时依赖上述 guard 的明确结构。它不是 owned-process worker 的实现，也不证明任意 FFI 已终止。

### e2f3598 的代码语义与证据

**独立定位：** `/Users/vincentadamnemessis/AI Projects/Real Computer Use/crates/rcu-agent/src/runtime.rs:50–108`（e2f3598）。

`StateOwner` 只在 try_lock 成功后构造；正常 Drop 显式 unlock。它是 Runtime 最后析构的字段，位于 contexts/ledger/domains 之后；启动及 offline repair 的错误路径也由该 guard 处理。没有删除锁文件、重试抢锁或忽略活 owner 的失败。

文件的复制/继承描述符可能延续锁的寿命，显式 unlock 可在不依赖最后一个描述符关闭的情况下释放锁，符合 Rust 官方 API 语义。[Rust File 锁文档](https://doc.rust-lang.org/std/fs/struct.File.html#method.unlock)

新增 Unix duplicate-descriptor 测试确认：活 owner 仍阻止新 owner；逻辑 owner Drop 后，旧副本不再拖延下一任；关闭旧副本不会解除新 owner 的锁。该测试和新一轮完整 gates 通过。

**归因限度：** 原失败与并发创建 crash 子进程时的短暂描述符继承有关，仍只是候选解释，本轮没有观察或追踪那次具体 fork 时序。这里接受的是明确的 orderly ownership 释放语义和已有确定性测试，不把推断写成已证实根因。未来 A01 若把有意继承的句柄用于独立 worker 所有权，必须重新明确交接/终止规则，不能把此次 unlock 当作子进程已停止的证明。
