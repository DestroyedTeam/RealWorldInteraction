## 确认的问题与下一轮整改顺序

1. **原生 UIA 覆盖不足。** 初始报告明确写出 `128 nodes / 1500 ms cooperative
   traversal budget`，且多个时点 `native_complete: false`。确认对话框按钮
   未及时进入可用语义集合，任务额外走了图像映射/记录查询。尚未分辨某次截断
   具体由节点数还是时间预算触发。应改进通用模态/交互区域的观察和输出，不能
   把 Task Manager、某个按钮名或这个清理任务写进产品后端。
2. **按键能力和拒绝信息不完整。** 实际 F5 返回 `unsupported_chord`，
   `native_dispatch_entered: false`。源码 `rcu-windows/src/input_plan.rs` 的
   chord 映射仅列出 F4/F10，没有 F5；这是原生输入能力缺口，不是 MCP 安装问题。
3. **错误表达增加恢复成本。** 上述结果同时包含 `dispatch: uncertain`、
   `system_accepted: null`、`is_error: false` 和嵌套 `dispatch_error`，SDK 最初
   只能报告笼统 `operation_failed`。未处理异常丢弃 JS 状态，随后又要查询原记录、
   获取 targets、重新绑定/观察。应梳理预派发拒绝、原生执行不确定性和 JS 异常的
   区分，保留原始执行引用，避免不必要的重新准备。
4. **保持即时校验，不用放宽它“优化”。** 一次坐标确认未获成功确认，另一处
   `checked_precondition_changed` 拒绝了变更中的状态；任务查询原记录后使用
   新观察继续。不能通过重放、隐藏错误或删除身份/焦点校验来压低耗时。
5. **继续以整轮指标验收。** 外部工具次数和文本已减少，但图像变多、模型/Host
   间隔更长。应结合下一步所需的紧凑观察、清晰的错误与持续对象 API 改进；
   不能从本轮数据推断“只是传输慢”，也不能将图像数量与延迟视为已证实因果。

这次证明了新任务里新 JS MCP 的真实 GUI 可用性和清理结果，**没有证明性能目标
已经达成**。上述问题记录后再整改，不在同一个正在运行的样本中更换被测产品。
GUI 与 terminal 的产品关系仍然是并列互补；此次没有把未实现的 SSH 通道算作
验收成功。
